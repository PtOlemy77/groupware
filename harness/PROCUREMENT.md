# 입찰공고 관리·나라장터 연동

## 사용 범위

모든 로그인 사용자는 `입찰공고 관리 → 관심 키워드 설정`에서 본인 관심조건을 등록·수정·삭제한다. 기관명/기관코드, 포함 키워드, 제외 키워드를 쉼표 또는 줄바꿈으로 입력한다. 각 목록 내부는 OR이며, 기관과 키워드 사이의 AND/OR는 별도로 선택한다. 둘 중 한 목록만 입력하면 그 목록만 적용한다. 제외 키워드는 공고명에서 항상 우선한다. 기관명은 포함 검색이고, 제공되는 기관코드는 정확히 비교한다. 사전규격에는 기관코드가 없을 수 있으므로 기관명을 함께 등록한다.

대상은 물품·용역·공사·외자의 사전규격과 입찰공고다. 공고명(사전규격은 품명/사업명)을 검색하며 첨부파일 본문 검색은 제공하지 않는다. 개인당 조건 50개, 각 키워드/기관 목록 30개, 항목당 100자까지 저장한다.

일치한 공고는 개인별 `공고·알림`에 저장한다. 목록은 전체 가로폭을 사용하는 압축 표이며 구분·사업명·기관·등록일·마감일·사업금액·원문 7개 열을 표시한다. 기관은 수요기관을 우선하고 없으면 공고기관을 표시한다. 한 페이지는 최대 100건이며 모바일에서는 표 내부를 가로로 이동한다. 상단에는 활성 관심조건의 키워드·기관을 중복 제거해 배치하고 클릭하면 저장된 공고를 검색한다. 관심조건 관리 화면도 압축 표로 제공한다. 자동 조회 주기·연동 상태 안내 영역과 목록의 감지 시각·일치 조건·공고 상태 설명은 표시하지 않는다.

공고 상세창 없이 목록의 원문 링크를 새 탭으로 연다. 원문 클릭 시 읽음 상태를 DB에 저장하므로 새로고침과 재시작 후에도 유지된다. 상단 종 아이콘은 로그인 상태에서 60초마다 개인별 미읽음 건수를 확인한다. 공통 알림창에는 메뉴 단위의 `입찰공고 알림 N건` 한 항목을 표시한다. 건수를 누르면 사전규격을 포함한 전체 공고의 개인 미읽음 목록 첫 페이지로 이동하고 검색어·종류·업무 조건을 초기화한다. 인사평가·일정 등 다른 메뉴의 알림 생성은 이번 추가 범위가 아니다. 선택한 필터는 URL에 반영해 새로고침 후에도 유지한다. 같은 공고가 여러 관심조건에 맞아도 사용자에게 한 번만 알린다. 변경일/차수·내용이 바뀌면 별도 변경본으로 알리고 원본은 보존한다. 관심조건 삭제는 기존 공고·알림을 삭제하지 않는다.

이 기능은 그룹웨어 내부 알림이다. 이메일·문자·앱 종료 중 OS 푸시는 발송하지 않는다. 서버가 중지되어 있는 동안에는 외부 API를 조회하지 않는다.

## 공식 API 기준 (2026-11-09 확인)

- [나라장터 입찰공고정보서비스](https://www.data.go.kr/data/15129394/openapi.do), 참고문서 1.3: `https://apis.data.go.kr/1230000/ad/BidPublicInfoService02/getBidPblancListInfo{Servc|Thng|Cnstwk|Frgcpt}02`.
- [나라장터 사전규격정보서비스](https://www.data.go.kr/data/15129437/openapi.do), 참고문서 1.0: `https://apis.data.go.kr/1230000/ao/HrcspSsstndrdInfoService/getPublicPrcureThngInfo{Servc|Thng|Cnstwk|Frgcpt}`.
- 기관 검색은 입찰 `getBidPblancListInfo{Servc|Thng|Cnstwk|Frgcpt}PPSSrch02`와 사전규격 `getPublicPrcureThngInfo{Servc|Thng|Cnstwk|Frgcpt}PPSSrch`를 사용한다. `inqryDiv=1`은 입찰 검색에서 공고게시일시, 사전규격 검색에서 접수일시다. 공고/수요 기관명은 `ntceInsttNm`/`dminsttNm`, 코드는 `ntceInsttCd`/`dminsttCd`를 개별 요청으로 전달한다. 기본 목록은 `inqryDiv=1`(등록일), `3`(변경일)을 사용하며 검색 오퍼레이션에 변경일 구분 3을 전달하지 않는다. 날짜는 `YYYYMMDDHHmm` 한국 시간이다. 공식 Swagger 및 참고문서의 요청/응답 필드를 대조했다. JSON 배열과 `items.item` 응답을 처리한다. API 오류·응답 누락·다른 페이지 응답은 성공으로 처리하지 않는다.
- API 문서상 개발계정 기본 트래픽은 1,000이며 승인·운영계정 한도는 공공데이터포털에서 실제 계정 기준으로 확인한다. 실제 수신은 승인된 인증키로 별도 확인해야 한다.

## 설정과 실행

백엔드 실행 환경에 다음 값을 설정한다. 실제 인증키를 Git·브라우저 코드·화면·로그에 넣지 않는다. 프론트의 `VITE_` 환경변수로 전달하지 않는다.

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| `G2B_SERVICE_KEY` | 비어 있음 | 두 서비스 활용신청이 승인된 일반 인증키(Decoding). 비어 있으면 API 호출 없음 |
| `G2B_ENABLED` | `true` | 서버 자동 조회 사용 여부 |
| `G2B_INTERVAL_MS` | `3600000` | 기본 60분 간격; 5분~24시간 범위 |
| `G2B_BUSINESS_TYPES` | `SERVC,THNG,CNSTWK,FRGCPT` | 조회 업무 코드. 용역만 필요하면 `SERVC` |

두 서비스의 활용신청 승인 후 인증키를 서버 환경에 넣고 백엔드를 재시작한다. 신규 설치/업데이트는 기존 DB 백업 및 적용 이력 확인 후 Flyway V9를 적용한다. V9는 새 테이블과 조회 소스 메타데이터만 만들며 기존 직원·프로젝트·휴일 행은 변경하지 않는다. `DataInitializer`는 변경하지 않는다.

인증키·활성 조건이 있을 때 시작 60초 후 첫 예약 작업을 요청하고 이후 설정 간격으로 확인한다. 실제 처리 중에는 중복 실행을 막는다. 관리자·임원은 `지금 공고 확인`으로 수동 조회를 요청할 수 있다. 호출 한도를 추가로 소비하므로 수동 조회를 반복하지 않는다.

활성 사용자 조건과 관련된 업무/공고 종류만 조회한다. 등록된 기관마다 공고기관과 수요기관을 나누어 API에서 먼저 검색한 뒤, 응답의 사업명에 키워드·제외어 및 최종 조건을 적용한다. 이름과 코드가 모두 가능한 영문/숫자 입력은 이름 검색과 코드 검색을 모두 요청한다. 여러 사용자 조건의 동일 기관 요청은 합친다. 기관이 없는 키워드 전용 조건, 또는 기관 OR 키워드 조건은 기관 밖의 일치 공고도 필요하므로 날짜별 기본 목록 전체 조회도 수행한다.

기관별 조회는 매 실행 시 최소 최근 7일을 다시 확인하고, 한 페이지 999건으로 전체 결과의 마지막 페이지까지 처리한다. 1,000건 또는 실행당 페이지 수로 결과를 자르지 않는다. 한 조회의 시작·종료 시각을 고정하고 실패하면 그 구간과 페이지를 서버에 보존하여 다음 실행에서 이어받는다. 한 주 재조회나 공고/수요 기관 검색에서 겹친 공고는 기존 고유키로 중복 알림을 막고 읽음 상태를 보존한다. 관심조건 추가·수정 시 해당 조건 집합의 조회 식별자를 새로 계산하여 최근 7일을 첫 페이지부터 다시 검색한다. 기존 공고·읽음·과거 조회 위치는 삭제하지 않는다.

별도 변경일 피드는 기본 목록 API로 마지막 성공 이후 변경분을 확인하여 최근 7일보다 오래된 공고의 정정도 감지한다. 첫 조회는 7일이며, 서버 중단으로 밀린 기간은 7일 구간으로 이어받는다. 기관 검색의 완료 구간도 장기 중단 후 밀린 범위가 있으면 이를 먼저 처리한다. 주간 전체 재조회는 기관 수·조건·전체 페이지 수에 비례하여 호출량이 달라지므로 기존 고정 최대 768회/일 계산은 적용하지 않는다. 승인 한도에 맞춰 주기와 업무 범위를 설정한다. 한도 오류가 발생한 구간은 성공으로 처리하거나 건너뛰지 않는다.

외부 요청은 DB 트랜잭션 밖에서 수행한다. 각 페이지의 일치 공고·사용자별 알림·다음 조회 위치는 한 트랜잭션으로 저장한다. 실패 시 해당 페이지를 건너뛰지 않는다. DB의 실행 lease와 사용자/공고 고유 제약으로 중복 작업을 방지한다. API 키와 원본 담당자 연락처는 저장하지 않으며 오류 메시지는 인증키가 포함된 URL을 노출하지 않는다.

나라장터가 HTTPS 상세 링크를 제공하면 해당 공고로 연결한다. 사전규격 등 상세 링크가 없는 응답은 공고번호와 나라장터 검색 진입 링크를 제공하며 추정 상세 URL을 만들지 않는다.

## 검증 범위와 제한

[Java 통합 테스트](../backend/src/test/java/com/nexus/groupware/ProcurementIntegrationTest.java)는 개인별 권한·CSRF·version·중복/변경 알림·읽음·동시 작업 실행권·실패 재시도·다음 페이지를 검사한다. [API 파싱 테스트](../backend/src/test/java/com/nexus/groupware/ProcurementGatewayTest.java)는 공식 필드 이름을 사용한 합성 응답·비정상 응답·URL 제한·키워드 조건을 검사한다. [PostgreSQL 테스트](../tests/procurement-migration.test.mjs)는 기존 데이터 보존·고유 제약·FK·관심조건 삭제 후 알림 이력 보존을 검사한다.

[브라우저 검사](../tests/procurement.e2e.cjs)는 관심조건 CRUD·API 미설정 시 수동 조회 비활성화·입찰/사전규격 감지·중복/제외·검색·읽음·새로고침·390px 화면을 검사한다. 공고 7열 표·키워드 전체 폭과 클릭 검색·합성 107건의 100건/7건 페이지 이동·행 높이도 확인한다. 원문 새 탭·상세창 제거·메뉴 단위 개인 미읽음 건수·읽음 후 건수 감소·숫자 클릭 목록 이동·동일 조건 재선택 시 검색 초기화·새로고침 필터 복원·알림창 키보드 닫기와 포커스 복귀도 검사한다. 테스트 전용 수집 입력은 테스트 클래스패스에만 있고 H2 메모리 DB에서만 허용한다. 프로덕션 JAR에는 포함하지 않는다. 테스트에 실제 직원이나 실제 API 키는 사용하지 않는다. 실제 공고 수신 속도·누락 여부·API 쿼터·서비스 승인·운영 서버 상시 실행은 합성 테스트로 보증하지 않는다.

2026-11-09 로컬 개발 DB는 Git 제외 경로 `backups/groupware-before-procurement-20261109.dump`에 백업한 후 기존 V0~V8 적용 이력을 확인하고 Flyway V9를 적용했다. 초기화는 비활성화했다. 새 관심조건·알림은 0건으로 시작하며 기존 휴일 374건과 2040년 범위는 보존되었다. 서버 헬스 200, 비로그인 공고 API 401 및 프로덕션 JAR의 테스트 입력 클래스 미포함을 확인했다. 실제 API 인증키는 설정하지 않았다. 상세 검증 결과는 [하네스 기준](HARNESS_ENGINEERING.md)에 기록했다. 운영 배포는 수행하지 않았다.

같은 날 추가로 사용자가 제공한 이미지에서 옮긴 키를 로컬 `.env`에 저장하고 URL 디코딩 후 두 서비스의 용역 목록을 최소 건수로 직접 호출했다. 파일은 Git 제외·소유자 읽기/쓰기 권한(0600)이며 키와 응답의 공고/담당자 자료는 기록하지 않았다. 두 API 모두 HTTP 403, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`, `returnReasonCode=30`(등록되지 않은 서비스키)을 반환했다. 네트워크 요청 도달은 확인했으나 인증 성공·실제 공고 수신은 확인하지 못했다. 이미지 문자 판독과 포털 키 등록/승인 상태를 구분하려면 정확한 인증키 텍스트 확인이 필요하다. 기존 실행 서버는 유지했고 새 키를 로드하는 재시작은 보류했다.


추가 재검증에서 사용자가 로컬 설정에 다시 붙여넣은 키로 입찰공고 API의 용역·물품·공사·외자 네 업무가 모두 HTTP 200 / 정상 코드 00으로 인증되었다. 사전규격 API는 같은 키에 대해 HTTP 403 / 오류 30을 반환하여 해당 서비스 활용승인 상태 확인이 필요하다. 검증된 키는 Decoding 형태로 정규화하여 비공개 환경설정에 보관하고 백엔드에 적용했다. 실제 공고·기관 담당자 자료는 로그나 검증 문서에 저장하지 않았다.

실제 입찰공고 API는 `numOfRows=1000` 요청 시 페이지 크기 10을 반환했고, 1·100·999 요청은 각각 정상 적용되었다. 수집 클라이언트는 999건을 요청하도록 정정했으며 응답의 실제 페이지 크기를 기준으로 다음 페이지를 계산한다. 인증 성공과 공고 수신 확인은 입찰공고 서비스에 한정하며 사전규격 성공으로 표현하지 않는다.

수정된 실제 Java 수집 클라이언트로 용역·물품·공사·외자의 등록일/변경일 조회 8종을 DB 연결 없이 실행하여 정상 파싱과 페이지 크기 999를 확인했다. 인증키를 불러온 로컬 서버 재시작 후 헬스 응답 200·비로그인 공고 API 401을 확인했다. 공개/추적 대상 파일과 백엔드 로그에 인증키가 없음을 검사했다. 당시 활성 관심조건은 0건이므로 실제 사용자 알림 생성 여부까지 검증한 것은 아니다. `npm run verify:full`은 Node/SQL 50건·Java 39건·빌드·격리 브라우저 검증까지 통과했다. 사전규격 서비스의 오류 30은 미해결 상태이며 해당 API의 활용승인 상태 확인이 필요하다.

공고 상세창 제거와 원문 목록 링크·카테고리 알림 변경 후 `npm run verify:full`이 Node/SQL 56건·Java 40건·JAR·프론트 빌드·격리 브라우저까지 통과했다. 합성 자료의 데스크탑 목록 및 모바일 알림창 이미지를 확인했다. 카테고리 집계와 업무 필터 API만 확장했으며 DB 스키마와 기존 업무 데이터는 변경하지 않았다.

기관별 주간 검색 변경에서 실제 Java 클라이언트의 입찰공고 네 업무 PPSSrch02 호출을 읽기 전용으로 실행하여 7일 범위·기관 조건·999건 페이지 설정의 정상 파싱을 확인했다. 실제 공고나 인증키는 기록하지 않았으며 DB 저장은 수행하지 않았다. 사전규격 활용승인 제한은 앞서 기록한 상태와 같다. 합성 회귀 검사는 2,005건의 마지막 페이지 일치·중간 실패 위치 재개·7일 재검색 중복 방지·조건 변경 후 주간 재검색·장기 중단 구간 보존을 포함한다.

주간 검색·메뉴별 단일 알림의 최종 `npm run verify:full`은 Node/SQL 56건·Java 43건·빌드·격리 브라우저까지 통과했다. 모바일 알림 이미지와 원문 링크의 새 탭·읽음 갱신도 합성 자료로 확인했다.
